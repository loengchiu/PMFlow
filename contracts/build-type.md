# 建设类型判定契约

solution-writer 和 solution-reviewer 共用。所有进入方案阶段的项目必须完成建设类型判定。

## 1. 三类建设类型

| 类型 | 英文标识 | 含义 |
|------|---------|------|
| 新建 | new_build | 部署、代码、数据库、实例均为全新 |
| 迭代 | iteration | 在已有系统上修改，沿用现有部署和数据库 |
| 混合 | hybrid | 部分模块新建、部分模块迭代 |

## 2. 四维度判定

建设类型必须按四个维度逐项判定，不得仅凭"参考旧系统"或"新开项目"一句话判定。

| 维度 | 判定问题 | 新建 | 迭代 |
|------|---------|------|------|
| 部署 | 是否部署到已有运行环境？ | 新环境 | 已有环境 |
| 代码 | 是否基于已有代码库修改？ | 新代码库 | 已有代码库 |
| 数据库 | 是否沿用已有数据库/表结构？ | 新数据库 | 已有数据库 |
| 实例 | 是否使用已有应用实例？ | 新实例 | 已有实例 |

## 3. 判定规则

### 3.1 新建（new_build）

四个维度全部为"新"。

**常见误判**：参考了旧系统的业务规则，但部署、代码、数据库、实例全部独立 → 仍为新建。旧系统参考不等于迭代。

### 3.2 迭代（iteration）

四个维度全部为"已有"或大部分为"已有"。

### 3.3 混合（hybrid）

部分维度为"已有"、部分为"新"。

必须明确标注：
- 哪些模块/页面是新建
- 哪些模块/页面是迭代
- 新建部分和迭代部分的边界

## 4. 判定依据

判定结果必须写入 metadata：

```yaml
build_type: new_build | iteration | hybrid
build_type_evidence:
  deploy: new | existing
  code: new | existing
  database: new | existing
  instance: new | existing
  hybrid_detail: 仅 hybrid 时必填，标注各模块类型
```

## 5. 与 BRD 范围的关系

- 建设类型判定必须与 BRD 的 scope_boundary 一致
- 如果 BRD 范围只覆盖新建部分，建设类型不应判为 hybrid 而应判为 new_build
- 如果 BRD 范围覆盖了迭代和新建两部分，建设类型必须判为 hybrid

## 6. 禁止事项

- 不得仅凭"新项目立项"判为新建
- 不得仅凭"参考旧系统业务规则"判为迭代
- 不得在未逐项判定四维度的情况下给出建设类型
- 不得将 hybrid 当作 new_build 或 iteration 的简化写法
