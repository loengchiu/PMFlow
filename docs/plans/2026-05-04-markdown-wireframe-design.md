# PMFlow Markdown 线框说明稿设计

日期：2026-05-04

## 1. 设计结论

PMFlow 的 `wireframe` 阶段产出一份 Markdown 线框说明稿：

```text
output/wireframe/wireframe.md
```

它位于 `design` 和 `prd` 之间：

```text
input -> align -> design -> wireframe -> prd -> prototype
```

它的目标是让 PM 在写正式 PRD 前，用一份可以直接阅读和修改的文档检查页面结构、页面跳转、字段落点、操作入口、状态表达和流程闭合情况。

`wireframe.md` 不是视觉稿，也不是可交互原型。它是一份页面结构验证稿。

## 2. 产物形态

`wireframe.md` 由四类内容组成：

| 内容 | 作用 |
|---|---|
| 页面跳转树 | 快速查看页面之间如何进入、返回和衔接 |
| 主流程说明 | 按页面和动作走一遍 P0/P1 主流程 |
| 页面结构草图 | 用 ASCII 表达关键页面区域、字段、操作和状态位置 |
| 落点表与疑点 | 检查字段、操作、状态是否有页面承载，并记录设计疑点 |

这四类内容共同回答一个问题：

```text
design 中的设计落到页面上后，是否仍然成立。
```

## 3. 信息来源

`/pm-wireframe` 从已通过 review 的 design 生成线框说明稿。

读取范围：

- `output/design/design.md`
- `.pmflow/metadata/design/index.yaml`
- design metadata 中的页面、字段、流程、状态、操作、规则分片
- 最近一次 design-review 结果

生成前需要确认 design-review 为 `pass` 或 `warn`，且 review 绑定当前最新 design 产物和 metadata。

`wireframe` 只投影 design 中已经存在的信息。生成过程中发现页面、字段、操作、状态或规则缺口时，记录到设计疑点。

## 4. 文档结构

`wireframe.md` 推荐结构如下：

```text
# 需求线框说明稿

## 1. 覆盖范围
- 来源 design：
- 覆盖模块：
- 覆盖页面：
- 覆盖主流程：
- 本次简化说明：

## 2. 页面跳转树

## 3. 主流程说明

## 4. 页面线框

### P1 页面名称

#### 页面跳转
来源：
- ...

去向：
- ...

#### 页面结构
[ASCII 草图]

#### 字段 / 操作 / 状态落点
| 类型 | 名称 | 页面落点 | 备注 |
|---|---|---|---|

#### 设计疑点
- ...

## 5. 设计疑点汇总
| 编号 | 问题 | 影响页面 | 建议处理 |
|---|---|---|---|
```

`.pmflow/metadata/wireframe/index.yaml` 记录必要的机读索引：

- 来源 design artifact。
- 来源 design metadata。
- 覆盖页面。
- 覆盖流程。
- 页面与 design anchor 的映射。
- 字段 / 操作 / 状态落点映射。
- 设计疑点索引。

metadata 只做索引，不复制完整线框正文。

## 5. 页面跳转树

页面跳转树用缩进文本表达页面关系。

示例：

```text
P1 触摸屏信息首页
  ├─ 查看信息详情 -> P2 服务区详情页
  ├─ 意见反馈 -> P3 意见反馈填写页
  └─ 满意度调查 -> P7 满意度问卷页

P3 意见反馈填写页
  └─ 提交成功 -> P4 意见反馈提交成功页
       ├─ 返回首页 -> P1 触摸屏信息首页
       └─ 参与满意度调查 -> P7 满意度问卷页
```

页面跳转树要覆盖：

- 主入口页面。
- 主流程涉及的页面。
- 成功页、失败页、返回页。
- 关键跨页面跳转。

## 6. 主流程说明

主流程说明按用户动作和页面流转写成编号步骤。

示例：

```text
流程：意见反馈

1. 用户从 P1 触摸屏信息首页点击“意见反馈”。
2. 系统进入 P3 意见反馈填写页。
3. 用户选择反馈对象。
4. 系统根据反馈对象展示问题类型。
5. 用户选择问题类型，填写补充说明。
6. 用户提交反馈。
7. 系统进入 P4 意见反馈提交成功页。
8. 用户可以返回首页，也可以继续参与满意度调查。
```

主流程说明要让 PM 看到：

- 入口在哪里。
- 每一步在哪个页面发生。
- 用户做什么。
- 系统响应什么。
- 成功后去哪里。
- 异常或取消时如何处理。

## 7. 页面结构草图

页面结构草图用 ASCII 表达关键页面区域。

示例：

```text
P3 意见反馈填写页

┌──────────────────────────────┐
│ 意见反馈                      │
├──────────────────────────────┤
│ 微信授权提示区                │
│ 仅小程序 / 二维码入口显示     │
├──────────────────────────────┤
│ 反馈对象 *                    │
│ [环境卫生] [餐饮服务] [...]   │
├──────────────────────────────┤
│ 问题类型 *                    │
│ 根据反馈对象级联显示          │
├──────────────────────────────┤
│ 补充说明                      │
│ [最多 200 字，选填]           │
├──────────────────────────────┤
│                       [提交]  │
└──────────────────────────────┘
```

页面结构草图优先覆盖：

- 入口页。
- 表单页。
- 结果页。
- 汇总页。
- 状态差异明显的页面。
- 容易被误解的页面。

普通列表、详情、维护页面可以按页面模式简写，避免线框稿过长。

## 8. 字段 / 操作 / 状态落点表

落点表用于检查 design 中的关键对象是否能落到页面上。

示例：

| 类型 | 名称 | 页面落点 | 备注 |
|---|---|---|---|
| 字段 | 反馈对象 | 反馈对象选择区 | 必填 |
| 字段 | 问题类型 | 问题类型选择区 | 根据反馈对象级联 |
| 字段 | 补充说明 | 补充说明输入区 | 选填，200 字以内 |
| 操作 | 提交 | 底部操作区 | 成功后进入 P4 |
| 状态 | 未授权 | 微信授权提示区 | 仅小程序 / 二维码入口 |

落点表比草图更适合发现遗漏：

- 字段是否有输入或展示位置。
- 操作是否有入口。
- 操作结果是否有去向。
- 状态是否有展示或处理区域。
- 同一字段或操作是否在多个页面重复出现并需要一致处理。

## 9. 设计疑点

线框说明稿生成过程中发现的问题进入设计疑点。

疑点表达为：

```text
问题：
影响页面：
影响流程：
为什么在页面层暴露：
建议处理：
```

示例：

```text
问题：反馈对象与问题类型存在级联关系，但 design 未定义具体映射表。
影响页面：P3 意见反馈填写页、P5 意见反馈汇总页。
影响流程：意见反馈提交、反馈统计。
为什么在页面层暴露：P3 必须根据反馈对象展示问题类型选项，当前无法判断选项集合。
建议处理：回到 design 补充反馈对象与问题类型映射。
```

设计疑点不直接补设计。它为 PM 和后续 `/pm-fix` 提供定位依据。

## 10. 生成完成后的输出

`/pm-wireframe` 完成后输出：

```text
已完成：
- 生成 output/wireframe/wireframe.md
- 生成 .pmflow/metadata/wireframe/index.yaml

需要 PM 查看：
- 页面跳转树是否符合预期
- 关键页面结构是否容易理解
- 字段 / 操作 / 状态落点是否完整
- 设计疑点是否需要回到 design 处理

下一步建议：
- /pm-wireframe-review
```

阶段完成后停止，由 PM 手动执行下一命令。

## 11. review 方法

`/pm-wireframe-review` 审查线框说明稿是否完成了页面结构验证。

检查项：

| 检查项 | 目标状态 |
|---|---|
| 页面覆盖 | 核心页面都出现在页面跳转树或页面线框中 |
| 主流程 | P0/P1 主流程能从入口走到结果 |
| 字段落点 | 关键字段有输入、展示或统计位置 |
| 操作落点 | 关键操作有入口和结果 |
| 状态落点 | 关键状态有展示或处理位置 |
| 事实一致 | wireframe 内容能追溯到 design |
| 疑点记录 | 页面层暴露的问题被清楚记录 |

判定口径：

| verdict | 目标状态 | 下一步 |
|---|---|---|
| pass | 页面结构和主流程成立，未发现 design 层阻断问题 | 建议 `/pm-prd` |
| warn | 有轻微表达风险或待确认问题，但不影响 PRD 写作 | 记录风险，建议 `/pm-prd` |
| fail | 页面、流程、字段、操作或状态存在 design 层阻断问题 | 建议修 design 或 wireframe |

review 结果必须写入 `.pmflow/reviews/`，并追加到 `status.review_results`。

## 12. 对 PRD 的影响

`/pm-prd` 读取：

- `output/design/design.md`
- design metadata
- `output/wireframe/wireframe.md`
- wireframe metadata
- 最近一次 wireframe-review 结果

PRD 的事实源是 design 和 design metadata。

wireframe 为 PRD 提供：

- 页面结构理解。
- 页面跳转顺序。
- 字段 / 操作 / 状态落点。
- PM 在页面层发现的疑点和处理意见。

wireframe-review 为 `fail` 时，PRD 写作应先暂停，因为页面层已经发现 design 或线框结构存在阻断问题。

## 13. 对 prototype 的影响

HTML prototype 在 PRD 后生成。

prototype writer 读取：

- design。
- wireframe。
- PRD。
- PM 在 PRD 或 wireframe 上提出的补充意见。

prototype 的目标是把已确认的 design、wireframe 和 PRD 表达成可交互页面。

PM 如果在 wireframe 或 PRD 中指出页面结构、跳转、字段或操作不合适，prototype writer 应优先吸收这些意见，并判断这些意见属于原型表达调整还是 design 事实变化。

## 14. 实现验收

后续实现完成后，应满足：

1. `/pm-wireframe` 生成 `output/wireframe/wireframe.md` 和 `.pmflow/metadata/wireframe/index.yaml`。
2. `wireframe.md` 包含页面跳转树、主流程说明、页面结构草图、字段 / 操作 / 状态落点表、设计疑点汇总。
3. `wireframe.md` 内容能追溯到 design，不把页面层新想法直接写成已确认设计。
4. `/pm-wireframe-review` 能区分线框表达问题和 design 层阻断问题。
5. wireframe-review pass/warn 后，`pm-guide` 推荐 `/pm-prd`。
6. wireframe-review fail 后，`pm-guide` 推荐修 design 或 wireframe。
7. `/pm-prd` 读取 wireframe，但以 design 为事实源。
8. `/pm-prototype` 读取 design、wireframe、PRD 和 PM 补充意见。
