# PMFlow PRD 写法与生成机制设计

日期：2026-05-04

## 1. 设计结论

PMFlow 的 PRD 阶段产出一份完整的人读主稿：

```text
output/prd/prd.md
```

这份 Markdown 是正式交付稿，后续用于转换 DOCX，给研发评审和公司归档。

PRD 的定位是：

```text
面向研发评审和归档的人读规格文档。
```

它不承担从零重新设计需求的职责。事实来源于 `design`，页面结构参考 `wireframe`，正文要写成自然、克制、可评审、可归档的产品规格说明，机读追溯由 `.pmflow/metadata/prd/` 承担。

PRD 的核心要求是：

- 人读正文自然、专业、像资深产品经理写的规格说明。
- 详细需求说明按模块、页面、用户动作展开。
- 字段在人读正文中自然出现，不暴露稳定 ID 或机读字段。
- 数据字典和详细需求说明必须能互相反查。
- 长文生成通过分块、摘要回收和 metadata 分片控制上下文。
- reviewer 既检查文风和完整性，也检查字段、规则、权限、验收和来源追溯。

一句话概括：

```text
整篇结构稳定、自然、克制；复杂动作要把状态、反馈、异常、边界写透；字段在人读正文里自然出现，机器在 metadata 中建立字段与页面、区域、动作的关系。
```

## 2. 写作风格

### 2.1 整体文风

PRD 正文采用资深产品经理的规格说明写法：

- 章节结构稳定，但正文不机械填空。
- 语言自然、克制、信息密度高，直接写规则、边界和结果。
- 页面先说明目标、关联功能点、区域职责。
- 详细需求说明按用户动作展开。
- 字段在动作和区域说明中自然出现。
- 简单动作短写，复杂动作展开校验、分支、状态变化和异常。
- 表格只用于状态流转、权限、数据字典、枚举、验收标准等天然映射内容。
- 不为了对称补空章节，不把简单动作写成复杂动作。
- 读者只看 PRD 就能理解本期做什么、怎么操作、状态如何变化、异常如何处理、如何验收。

### 2.2 动作级写法

动作说明按复杂度决定展开深度。复杂动作需要自然补齐：

- 默认状态和初始加载规则。
- 可点 / 不可点条件。
- 点击后的反馈、加载状态和防重复。
- 成功后的页面变化、数据变化和状态变化。
- 失败提示、错误字段、错误位置和保留输入规则。
- 表单字段、输入限制、校验时机和错误提示。
- 空状态、加载失败、超长文本处理。
- 弹窗打开、关闭、遮罩层行为和多弹窗优先级。
- 异步任务的进行中、完成、失败、离开页面后的处理。
- 权限不足、网络异常、边界值、并发冲突。

简单动作保持短写。例如：

```markdown
点击"下载模板"按钮，系统生成标准物资导入模板 Excel 文件，浏览器自动下载。
```

普通查询动作写清默认加载、筛选、排序、列表字段和空状态。例如：

```markdown
进入页面后，系统按当前筛选条件（入库状态、发起方式、目标服务区、关键字、申请时间范围）加载入库记录列表，默认按申请时间降序排列，每页 20 条。

列表展示入库申请单编号、入库申请名称、申请服务区、所在区域、发起方式、申请人、目标服务区、入库状态、申请时间、操作入口。无匹配数据时，列表区显示"暂无入库记录"。
```

复杂提交动作写清字段、校验、分支、状态变化和成功反馈。例如：

```markdown
服务区管理员点击"新增入库"按钮，打开入库申请弹窗，通过物资选择器从资产库选择标准物资，填写存放位置、数量、税后单价、备注后提交。

提交时校验：
· 标准物资不能为空
· 数量必须大于 0，且为整数
· 税后单价必须大于等于 0，保留 2 位小数
· 备注长度不超过 500 个字符

校验通过后，系统按明细逐条计算税后价值：
1. 任一明细税后价值大于 2000 元时，入库状态为"待财务审核"。
2. 全部明细税后价值均不大于 2000 元时，入库状态为"待确认"。

提交成功后弹窗关闭，列表刷新，提示"提交成功"。
```

### 2.3 生成与追溯机制

PRD 写作机制固定为：

- 分块生成。
- 页面级摘要回收。
- 按需读取 metadata 分片。
- 人读正文和机读追溯分离。
- 稳定 ID 只存在于 metadata。
- 字段、页面、动作、规则、验收之间用 `relations` 建立关系。
- reviewer 使用 metadata 做字段一致性、来源追溯和未确认扩展检查。

人读 PRD 不内嵌 trace block，不放 AI 锚点区，不展示内部路径。追溯全部写入 `.pmflow/metadata/prd/`。

## 3. 人读 PRD 结构

人读主稿固定为一份完整 Markdown：

```text
output/prd/prd.md
```

推荐骨架：

```text
# PRD：{项目名称}

## 一、文档概述
## 二、范围
## 三、业务流程
## 四、用户角色与权限
## 五、数据字典
## 六、详细需求说明
## 七、验收标准汇总
## 八、风险与待确认
```

按需出现：

```text
## 公共模块说明
## 系统依赖
## 非功能要求
## 数据影响范围
## 建议实施顺序
## 附录
```

无真实约束的章节不出现。追溯信息进入 metadata，不进入人读 PRD。

## 4. 详细需求说明写法

详细需求说明按：

```text
模块 -> 页面 -> 动作
```

页面开头采用以下写法：

```markdown
### （一）P-01 资产库管理页

**页面目标**：由运营部维护标准物资目录，作为服务区申请入库时的标准物资选择来源。

**关联功能点**：标准物资资料维护、标准物资批量导入、标准物资详情查看、标准物资编辑、标准物资删除控制

页面由筛选区、列表区、操作区组成。筛选区负责缩小查询范围，列表区负责展示标准物资摘要和引用状态，操作区负责新增、编辑、删除、导入、导出等动作。
```

动作标题使用动词短语：

```text
查询标准物资
新增标准物资
删除标准物资
财务审核入库
确认入库
```

动作正文按复杂度展开：

| 复杂度 | 写法 |
|---|---|
| 简单动作 | 1 句写清触发和结果 |
| 普通动作 | 1-2 段写清默认展示、字段、操作结果、空状态 |
| 复杂动作 | 补充校验列表、分支结果、状态变化、失败提示 |
| 高风险动作 | 补充权限、异常、并发、边界、回写影响 |

字段在正文中自然出现，例如：

```markdown
进入页面后，系统按当前筛选条件（入库状态、发起方式、目标服务区、关键字、申请时间范围）加载入库记录列表，默认按申请时间降序排列，每页 20 条。

列表展示入库申请单编号、入库申请名称、申请服务区、所在区域、发起方式、申请人、目标服务区、入库状态、申请时间、操作入口。无匹配数据时，列表区显示"暂无入库记录"。
```

这类写法是 PRD 正文的目标状态。字段不做额外摘要表，不写字段 ID，不把页面说明变成配置清单。

## 5. 数据字典与详细需求说明的关系

数据字典是字段主定义区。详细需求说明是字段的业务使用区。

人读 PRD 中：

- 数据字典集中定义字段的类型、必填、枚举、格式、默认值、业务来源和说明。
- 详细需求说明按页面、区域、动作自然描述字段出现在哪里、怎么使用。
- 关键字段规则只在影响操作、校验、权限、状态、异常或验收时展开。

机读 metadata 中必须建立字段落点关系（写入 pages/*.yaml）：

```yaml
pages:
  - id: PAGE-ASSET-LEDGER
    page_name: 服务区资产台账页
    regions:
      - name: 筛选区
        fields:
          - field_id: FIELD-ASSET-CODE
            field_name: 资产编码
            usage: 筛选
      - name: 列表区
        fields:
          - field_id: FIELD-ASSET-CODE
            field_name: 资产编码
            usage: 展示
  - id: PAGE-ASSET-DETAIL
    page_name: 服务区资产台账详情页
    regions:
      - name: 物资明细区
        fields:
          - field_id: FIELD-ASSET-STATUS
            field_name: 在库状态
            usage: 展示
```

这层关系用于：

- `/pm-prd-review` 双向检查数据字典和详细需求说明是否一致。
- `/pm-fix` 在字段变化后定位受影响页面、区域、动作、规则、验收标准。
- 后续 prototype 读取字段落点，不靠大段 PRD 正文猜页面字段。

## 6. PRD metadata 结构

PRD 生成时同步写入：

```text
.pmflow/metadata/prd/index.yaml
.pmflow/metadata/prd/dictionary.yaml
.pmflow/metadata/prd/pages/*.yaml
.pmflow/metadata/prd/rules.yaml
.pmflow/metadata/prd/trace.yaml
.pmflow/snapshots/prd/prd.last-synced.md
```

建议职责：

| 文件 | 职责 |
|---|---|
| `index.yaml` | 文件索引（只作为索引，不保存字段主定义） |
| `dictionary.yaml` | 字段主定义唯一来源 |
| `pages/*.yaml` | 页面、区域、动作、字段落点 |
| `rules.yaml` | 业务规则、异常、权限、验收标准 |
| `trace.yaml` | PRD 与 design、wireframe 的来源追溯关系 |
| `prd.last-synced.md` | 人读主稿同步快照 |

metadata 可以分片增长，人读 PRD 不拆分。

## 7. Writer 生成流程

`/pm-prd` 执行时按以下顺序生成：

1. 读取 `.pmflow/status.yaml`。
2. 校验 `workflow_mode: new_main`。
3. 校验 wireframe-review 为 `pass` 或 `warn`，且绑定当前最新 wireframe 产物和 metadata。
4. 读取当前 design 人读主稿和必要 metadata 分片。
5. 读取 wireframe 人读主稿和必要 metadata 分片。
6. 读取 PRD 写法规则和 PMFlow PRD 写法参考。
7. 规划 PRD 章节和页面生成顺序。
8. 先生成全局章节：文档概述、范围、业务流程、角色权限、数据字典。
9. 按页面逐块生成详细需求说明。
10. 每生成一个页面，同步写该页面 metadata、字段落点、页面摘要。
11. 生成验收标准汇总、风险与待确认。
12. 回查数据字典和详细需求说明的字段一致性。
13. 写入 `output/prd/prd.md`、`.pmflow/metadata/prd/`、`.pmflow/snapshots/prd/prd.last-synced.md`。
14. 更新 `.pmflow/status.yaml`：`current_stage: prd`、`artifacts.prd`、`snapshot_records`。
15. 输出下一步唯一建议：`/pm-prd-review`。

PRD writer 的事实源是 design。wireframe 提供页面结构、区域、跳转和疑点参考。

## 8. 上下文防爆

PRD 人读主稿可以很长，但 writer/reviewer 读取方式必须分块。

生成详细需求说明时：

```text
读取当前页面相关 design 分片
-> 读取当前页面相关 wireframe 分片
-> 生成当前页面正文
-> 写当前页面 metadata
-> 写当前页面摘要
-> 释放当前页面完整上下文
-> 进入下一页
```

writer 不一次性把完整 design metadata、完整 wireframe metadata、完整 PRD 草稿全部塞进上下文。

页面级生成需要保留：

- 当前页面相关字段。
- 当前页面相关动作。
- 当前页面相关状态。
- 当前页面相关规则。
- 当前页面相关验收点。
- 已生成页面摘要。
- 全局术语、角色、范围、状态流转摘要。

## 9. Reviewer 检查方式

`/pm-prd-review` 是独立 reviewer。它读取 writer 产物和 metadata，不复述 writer 自检。

检查项：

| 检查项 | 目标 |
|---|---|
| PRD 独立归档质量 | 研发只读 PRD 能理解需求、规则和边界 |
| PRD 文风一致 | 结构稳定、表达自然、动作按复杂度展开 |
| 字段一致性 | 数据字典与详细需求说明字段一一可追溯 |
| 字段落点完整 | 核心字段至少有页面、动作、规则、权限或验收落点 |
| 页面覆盖 | design 中核心页面在 PRD 中有章节 |
| 动作覆盖 | 页面关键动作有触发、结果、状态或异常说明 |
| 规则覆盖 | 业务规则、异常、权限、验收覆盖核心流程 |
| 来源追溯 | PRD 内容能追溯到 design 或 wireframe |
| 人机分离 | 人读 PRD 不暴露 metadata、内部路径、review 字段 |

字段一致性需要双向反查：

```text
数据字典字段 -> 页面/区域/动作/验收落点
详细需求说明字段 -> 数据字典主定义
动作规则中的字段 -> 数据字典和 pages/*.yaml
验收标准中的字段 -> 数据字典和页面动作
```

review pass/warn 后只提示 `/pm-prototype`。review fail 时回到 `/pm-prd` 或按问题建议 `/pm-fix`。

## 10. 验收标准

PRD 阶段实现完成后，至少满足：

1. `/pm-prd` 在 new_main 下不再是 placeholder。
2. `/pm-prd` 只在 wireframe-review pass/warn 且绑定最新产物时启动。
3. `output/prd/prd.md` 是完整人读主稿，可直接转换 DOCX。
4. PRD 文风自然、克制、信息密度高，不是填空模板。
5. 详细需求说明按模块、页面、动作展开。
6. 页面字段在正文中自然出现，不写字段 ID。
7. `.pmflow/metadata/prd/` 能记录字段与页面、区域、动作的关系。
8. 数据字典和详细需求说明可以双向反查。
9. `/pm-prd-review` 能发现字段字典与页面说明不一致。
10. PRD 人读稿不包含内部路径、metadata 字段、review 字段。
11. 大型 PRD 生成过程有页面级摘要和 metadata 分片，不依赖一次性全量上下文。
12. review pass/warn 后由 PM 手动执行 `/pm-prototype`，不自动推进。

## 11. 后续实现顺序

建议按以下顺序实现：

1. 更新 `templates/prd.md`，采用稳定、自然、可归档的 PRD 骨架，去掉 AI 锚点区。
2. 更新 `references/prd-writing.md`，记录自然写法、动作复杂度、字段自然落点。
3. 更新 `profiles/prd.profile.yaml`，切到 new_main 的 design/wireframe 前置口径。
4. 实现新主链 `/pm-prd` writer。
5. 实现 `.pmflow/metadata/prd/` 分片结构。
6. 实现新主链 `/pm-prd-review` reviewer。
7. 补充 E2E smoke 和字段一致性边界测试。
8. PRD 通过后再进入 prototype 设计。
