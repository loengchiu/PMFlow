# PRD 写法参考

本文件承接 ShitPM 和 OMP 已验证的 PRD 文风经验，只做 prd-writer 的写法参考。

## 1. 目标

PRD 是正式归档文档。研发、测试、需求方应能只读 PRD 理解规则和边界。

PRD 不能依赖原型才能读懂，也不能把业务规则推回 solution。

## 2. 主结构

推荐主骨架：

- 文档概述。
- 范围。
- 业务流程。
- 用户角色与权限。
- 数据字典。
- 详细需求说明。
- 验收标准。
- 风险与待确认。

按需出现：

- 公共模块说明。
- 系统依赖。
- 非功能要求。
- 数据影响范围。
- 附录。

无真实约束的按需章节不出现。

## 3. 详细需求说明

详细需求说明按：

```text
模块 -> 页面 -> 动作
```

页面开头可用一小段交代页面由哪些区域组成、各区域承担什么职责。后文按用户动作组织，不按 UI 区域逐项盘点。

动作标题用动词短语，例如：

- 查询入库记录。
- 发起入库申请。
- 提交审批。
- 驳回申请。

## 4. 动作写法

每个动作覆盖：

- 触发条件。
- 操作过程。
- 操作结果。
- 异常处理。

但不要机械写成四段填空。

简单动作 1-2 句带过；复杂动作写清顺序、状态、分支和中断。

## 5. 数据字典和页面字段

数据字典不是孤立字段表。

每个进入数据字典的业务字段，至少要在以下位置之一有落点：

- 页面字段。
- 页面动作。
- 权限矩阵。
- 状态流转。
- 验收标准。
- 风险与待确认。

字段新增、删除、改名、类型变化、必填变化、枚举变化、校验规则变化时，必须同步检查页面、动作、筛选、列表、详情、导入导出、权限、状态和异常。

## 6. 规则写法

PRD 中要直接写规则，不写空泛原因。

优先写：

- 展示什么。
- 谁能操作。
- 什么时候可点。
- 点击后发生什么。
- 成功后状态如何变化。
- 失败时提示什么。
- 边界值是什么。

少写：

- 方便用户。
- 用于承接。
- 提升体验。
- 按配置。
- 同常规。

## 7. 表格使用

表格适合：

- 数据字典。
- 权限矩阵。
- 状态映射。
- 枚举定义。
- 验收标准。

页面说明和操作说明优先用自然段、短列表和顺序列表。

## 8. 防幻觉

每个功能点、字段、页面、状态必须来自已确认的 BRD、UC、solution、prototype 或 PM 补充。

找不到依据时：

- 标记为待确认。
- 不得编造。
- 不得为了完整感补范围外内容。

## 9. 禁止表达

- “详见原型”
- “原型已说明”
- “按业务规则”
- “按配置”
- “同常规”
- “待定”
- “需支持”
- “后续完善”
- “等”

如果确实缺信息，写入待确认问题。
