# Prototype 写法参考

本文件承接 ShitPM 和 OMP 的原型经验，只做 prototype-designer 的写法参考。

## 1. 目标

原型先交付真实页面，再用标注解释关键点。

原型要让需求方和研发先看到：

- 页面长什么样。
- 从哪里进。
- 做什么操作。
- 操作后状态怎么变。
- 哪些字段在列表、详情、表单中出现。

## 2. 页面本体优先

好的原型打开后应先看到页面本体。

不要：

- 页面上方铺大段流程说明。
- 用大卡片解释“本页用于承接”。
- 标注和大纲挤压页面主体。
- 把原型做成讲解板。

可以：

- 左侧大纲可收起。
- 标注编号小、贴元素。
- 点击标注再看说明。
- 简单页面少标，复杂页面重点标。

## 3. 页面拆分

优先多页面独立 HTML，再共享 CSS/JS。

不要把所有页面堆在一个 HTML 里，后续修改和定位成本高。

建议：

- `index.html` 如需存在，只做页面入口。
- 每个主要页面独立 HTML。
- `shared.css` 负责公共视觉。
- `shared.js` 负责大纲、标注等公共交互。

## 4. 信息架构落地

prototype 必须承接 solution 的信息架构。

列表页：

- 展示字段按用户判断优先级排列。
- 筛选项只放常用判断维度。
- 行内操作只放当前状态下最常用动作。

详情页：

- 信息按业务分区。
- 关键状态、审批记录、操作入口位置清楚。
- 不把所有字段平铺成长表。

表单页：

- 字段按填写任务分组。
- 必填、校验、禁用、只读状态可见。
- 提交、取消、暂存等操作位置稳定。

## 5. 标注规则

标注只解释开发或评审需要注意的点，不替代页面主体。

标注适合放在：

- 关键字段。
- 关键按钮。
- 状态变化。
- 联动区域。
- 特殊校验。
- 和 PRD 需要对应的规则点。

不要给所有元素都加标注。

## 6. 状态和流程

原型至少要能走通主流程：

- 入口页。
- 列表定位。
- 详情或表单。
- 提交或审批。
- 结果或状态回流。

涉及审批时，要展示：

- 提交后状态。
- 审批中限制。
- 通过后可做什么。
- 驳回后回哪里。
